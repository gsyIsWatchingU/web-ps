# Doc Maintenance

用于约束项目文档职责、更新时机与开发后必须执行的文档回写流程。

## 文档职责

### `README.md`

- 面向外部读者
- 负责项目介绍、技术栈、快速开始、部署、状态边界、文档导航
- 不记录单次开发过程

### `docs/work-roadmap.md`

- 唯一的开发过程记录入口
- 按“一次可感知开发步”记录阶段总结
- 关注做了什么、验证了什么、还剩什么

### `docs/feature-list.md`

- 唯一的功能状态真相源
- 关注“当前有哪些功能、做到什么程度”

### `docs/plan-list.md`

- 唯一的计划与优先级真相源
- 关注“接下来先做什么、为什么做、被什么阻塞”

## 何时更新哪份文档

| 场景 | 必须更新的文档 |
| --- | --- |
| 完成一次开发任务 | `docs/work-roadmap.md` |
| 功能状态发生变化 | `docs/feature-list.md` |
| 优先级、阶段目标、下一步发生变化 | `docs/plan-list.md` |
| 项目启动方式、部署方式、对外介绍发生变化 | `README.md` |

## 每次开发结束后的必做动作

1. 在 `docs/work-roadmap.md` 追加本次开发记录
2. 检查本次是否改变了功能状态，如有变化则更新 `docs/feature-list.md`
3. 检查本次是否改变了优先级或下一步，如有变化则更新 `docs/plan-list.md`
4. 如果启动、部署、文档入口或项目定位变了，再更新 `README.md`

如果以上任一步未完成，则本次任务不算真正结束。

## 推荐更新顺序

1. `docs/work-roadmap.md`
2. `docs/feature-list.md`
3. `docs/plan-list.md`
4. `README.md`（仅在对外信息变动时）

## 格式规范

- 日期格式：`YYYY-MM-DD`
- 功能状态：`已完成 / 开发中 / 待开始 / 暂缓`
- 计划状态：`待处理 / 进行中 / 已完成 / 阻塞`
- 记录粒度：以“一次能被描述清楚的小步开发”为单位，不按零散提交碎片化记录
- 写法要求：优先写结论、改动、验证、遗留问题，避免长篇设计稿式叙述

## `work-roadmap` 记录模板

```md
### YYYY-MM-DD - 阶段标题

- 本次目标：
- 实际改动：
- 验证结果：
- 遗留问题：
- 下一步：
```

## 给大模型的固定收尾提示词

每次让大模型完成代码任务时，建议在需求末尾附上这段：

```text
完成代码后，请同步更新 docs/work-roadmap.md、docs/feature-list.md、docs/plan-list.md，并在回复中说明更新了哪些文档。
```

如果是涉及对外说明、部署、启动方式变化的任务，再补一句：

```text
如果项目介绍、启动方式、部署方式或文档入口有变化，也请同步更新 README.md。
```

## 文档边界提醒

- 不再新增零散计划稿、spec、ADR、模板文档作为长期维护资产
- 如果需要临时分析，可在任务过程中临时生成草稿，但任务结束前要把有效信息收敛进现有 4 份文档
- 新项目默认优先复用这套轻量文档结构，除非确实存在额外强约束
