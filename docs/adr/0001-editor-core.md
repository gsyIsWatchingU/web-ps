# ADR 0001: 编辑器内核选型

- Status: accepted
- Date: 2026-05-15
- Decision Makers: frontend

## Context

项目首版面向 AIGC 带货图文的二次精修，第一阶段重点是图层、花字、比例调整、基础滤镜、导出和历史操作。当前仓库从零开始搭建，需要在开发效率、交互稳定性和中期可扩展性之间做平衡。

备选方向：

- `Fabric.js`
- `Canvas/Konva + 自定义编辑行为`
- 其他偏图形场景的封装型编辑器框架

## Decision

首版采用 `Fabric.js` 作为编辑器内核，业务层不直接依赖 Fabric object，而是通过 `EditorDocument + Layer + Command` 这一层进行抽象。

## Why

- 首版核心能力以对象级编辑为主，Fabric.js 能较快覆盖图片、文字、基础变换和部分滤镜能力。
- 对于个人或 2 人小队，Fabric.js 的集成和调试成本更低，更适合快速验证 MVP。
- 首版主要目标是打通导入、编辑、保存、导出链路，而不是构建像素级图像编辑引擎。
- 通过文档模型和命令层隔离，可以降低未来替换底层渲染库的成本。

## Consequences

正向影响：

- 能更快搭建图层编辑、文字样式和导出能力。
- 可以在早期把精力放在产品闭环和工程文档，而不是底层绘制系统。

约束：

- 对于自由涂抹、局部重绘、复杂蒙版等像素级能力，Fabric.js 不是长期最优解。
- 若未来进入高频像素编辑场景，可能需要引入更底层的 Canvas 渲染能力甚至迁移内核。

## Triggers For Revisit

出现以下情况时，需要重新评估本决策：

- 产品明确要求大规模引入自由笔刷、局部蒙版、像素级调整。
- Fabric.js 在 10 到 20 图层下仍出现明显性能瓶颈且难以优化。
- 编辑器需要支持更复杂的离屏渲染、区域重绘或多视图同步。

## Follow-up

- 所有业务设计文档继续坚持“业务模型与渲染对象解耦”的约束。
- 当引入 AI 局部精修设计时，先在 spec/design 中评估是否触发本 ADR 的重审条件。
